# ADR-004: Use Alembic directly, not Flask-Migrate

**Status**: accepted
**Date**: 2025-01-01

## Context

Flask-Migrate is the standard extension for running Alembic with Flask. However, the project uses a custom `alembic/env.py` that imports models explicitly and sets up the SQLAlchemy metadata target. Flask-Migrate's `flask db migrate` command invokes Alembic through its own env, which does not see the custom configuration, resulting in empty (no-op) autogenerated migrations.

## Decision

Run Alembic directly via `.venv/bin/alembic`. Flask-Migrate is not used for migration generation or application.

```bash
.venv/bin/alembic revision --autogenerate -m "description"
.venv/bin/alembic upgrade head
```

Flask-Migrate is still installed (it initialises the Migrate object that ties Alembic to the app context at startup) but `flask db` CLI commands are never used.

## Consequences

**Positive**
- Autogenerated migrations correctly detect schema changes — no silent empty migrations
- Full control over `alembic/env.py` (enum handling, custom type decorators, etc.)

**Negative / trade-offs**
- Less discoverable: developers accustomed to `flask db migrate` will get empty migrations and may not understand why
- Must document clearly in CLAUDE.md to avoid the footgun

**Risks / open questions**
- None — this is stable and working. The risk is entirely documentation/onboarding.
